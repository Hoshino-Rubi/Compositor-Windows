# Compositor for Windows 0.4.1a6 — GPU Liquify/Smudge and Transfer Reuse

**Pre-release only. Stable Latest remains 0.4.0.**

## Added and improved

- **GPU Liquify and Smudge:** process larger brush segments on Direct3D 11 in 8/16-bit documents. Pixel work within a dab runs in parallel; successive dabs preserve their order and native-depth quantization. Only the affected local region plus sampling margins is transferred, with one readback per processed pointer-move segment rather than per dab.
- **Editing behavior:** path selections, feathered selection masks, layer/mask targets, and undo/redo retain the existing Windows behavior. Small operations, device/resource failures and `COMPOSITOR_DISABLE_GPU=1` use the CPU reference path without partial GPU edits.
- **Reusable processing transfers:** same-size/depth filter, effect and warp calls reuse their input, packed-output and readback textures. Inputs are uploaded each time, so changed images and parameters cannot return a stale cached result. Transfer resources are budgeted and released by cache clearing.
- Atkinson/Floyd–Steinberg and Camera Raw requests with active luminance denoising retain the **a5p1 CPU routing**; this batch does not repeat serial-GPU performance regressions.

## Validation and performance

Native and extracted-portable verification: the main Qt suite passes **131 tests with 0 failures and 1 optional HEIC-alpha fixture skipped**; the dedicated GPU-warp suite passes **11 tests with 0 failures or skips**. Coverage includes 8/16-bit CPU comparisons, actual GPU dispatch/readback assertions, offset ROI on a document above 8MP, path holes, feathered selection/mask targets, undo, low-resource fallback and processing-transfer cache invalidation. Same-size/depth repeated filter/effect calls allocate **zero new transfer textures** while still uploading and processing their current pixels.

Local warm-shader medians of three runs, **7 ordered dabs** per pointer-move segment, including ROI preparation, upload, GPU computation, readback and image writeback:

| Image / radius | Depth | Tool | CPU reference | GPU route |
|---|---:|---|---:|---:|
| 512×512 / 160px | 8 | Liquify | 21.41 ms | 2.39 ms |
| 512×512 / 160px | 8 | Smudge | 19.02 ms | 2.05 ms |
| 512×512 / 160px | 16 | Liquify | 24.39 ms | 3.30 ms |
| 512×512 / 160px | 16 | Smudge | 20.41 ms | 2.70 ms |
| 1024×1024 / 320px | 8 | Liquify | 87.66 ms | 5.23 ms |
| 1024×1024 / 320px | 8 | Smudge | 79.08 ms | 4.94 ms |
| 1024×1024 / 320px | 16 | Liquify | 94.96 ms | 7.00 ms |
| 1024×1024 / 320px | 16 | Smudge | 80.90 ms | 7.08 ms |

Each batch issues 7 warp dispatches and one image readback. The fixtures measured at most **1 native channel step** of CPU/GPU difference in both depths; this is measured coverage, not a universal pixel-identity guarantee. An 8.96MP document test uploaded only about **2.5MB (8-bit) / 3.8MB (16-bit), including the selection mask**, rather than its 35.8MB / 71.7MB full pixel buffer. Small/sparse strokes stay on CPU; timings depend on the GPU, brush/selection and system load. Shader compilation on first use is not included in warm timings.

## Scope and limitations

This batch ports the **existing Windows** Liquify/Smudge algorithm; it does not introduce macOS's persistent whole-stroke GPU textures, carried-color brush model or accumulated Liquify displacement field. Repeated Liquify resampling can still soften pixels. Results may differ slightly from CPU arithmetic at sample-rounding boundaries; the test bounds are reported above. Selection coverage preparation and applying returned pixels remain CPU work; readback is synchronous. Ordinary paint/eraser/clone/healing, perspective transforms and export remain CPU-backed.

GPU operations retain the a5 resampling/stroke-antialiasing differences and resource limits. The 8MP limit applies to the uploaded warp region, not the whole document; larger requests fall back to CPU. Transfer reuse is not caching every compute scratch texture and does not eliminate upload/readback or guarantee a speedup. No project-format, runtime dependency or interface-language change. Keep backups when testing.

## 0.4.1a6 — GPU 液化／涂抹与传输资源复用

**仅预发布；稳定版 Latest 保持 0.4.0。**

### 新增与改进

- **GPU 液化与涂抹：**较大的笔刷段在 Direct3D 11 上处理，支持 8／16 位。单个笔触内的像素并行计算，连续笔触保留原有顺序和原位深量化。只传输受影响局部区域及采样边界，一个鼠标移动段处理后回读一次，不再逐笔触传输。
- **编辑行为：**保留 Windows 现有路径选区、柔边选区蒙版、图层／蒙版目标以及撤销／重做。小范围操作、设备／资源失败和 `COMPOSITOR_DISABLE_GPU=1` 使用 CPU 参考路径，不留下部分 GPU 编辑。
- **处理传输资源复用：**同尺寸／位深的滤镜、图层效果和变形调用复用输入、打包输出和回读纹理；每次上传新像素，图像或参数变化不会返回过期结果。资源计入预算并随缓存清理释放。
- Atkinson／Floyd–Steinberg，以及实际启用亮度降噪的 Camera Raw 请求，继续使用 **a5p1 的 CPU 路由**，不再强制执行低效串行 GPU 计算。

### 验证与性能

原生构建与解压后便携包验证：主 Qt 测试均 **131 项通过、0 失败、1 项可选 HEIC-alpha 样本跳过**；独立 GPU 变形测试均 **11 项通过、0 失败、0 跳过**。覆盖 8／16 位 CPU 比对、真实 GPU 调度／回读、超过 8MP 文档的偏移局部区域、路径孔洞、柔边选区／蒙版目标、撤销、低资源回退和传输缓存失效。同尺寸／位深重复滤镜／效果调用 **不再分配新的传输纹理**，但仍上传和处理当前像素。

本机着色器预热后重复三次的中位数，每个鼠标移动段 **7 个顺序笔触**，包括局部区域准备、上传、GPU 计算、回读与图像回写：

| 图像／半径 | 位深 | 工具 | CPU 参考路径 | GPU 路径 |
|---|---:|---|---:|---:|
| 512×512／160px | 8 | 液化 | 21.41 ms | 2.39 ms |
| 512×512／160px | 8 | 涂抹 | 19.02 ms | 2.05 ms |
| 512×512／160px | 16 | 液化 | 24.39 ms | 3.30 ms |
| 512×512／160px | 16 | 涂抹 | 20.41 ms | 2.70 ms |
| 1024×1024／320px | 8 | 液化 | 87.66 ms | 5.23 ms |
| 1024×1024／320px | 8 | 涂抹 | 79.08 ms | 4.94 ms |
| 1024×1024／320px | 16 | 液化 | 94.96 ms | 7.00 ms |
| 1024×1024／320px | 16 | 涂抹 | 80.90 ms | 7.08 ms |

每个批次执行 7 次变形计算、一次图像回读。测试中两种位深相对 CPU 的最大差异均为 **1 个原生通道量化单位**；这只是已测范围，不是普遍逐像素一致保证。8.96MP 文档测试仅上传约 **2.5MB（8 位）／3.8MB（16 位），含选区蒙版**，而不是整图的 35.8MB／71.7MB 像素缓冲区。小范围／稀疏笔画保留 CPU；计时取决于显卡、笔刷／选区和系统负载，预热计时不含首次着色器编译。

### 范围与限制

本批迁移的是 **Windows 现有**液化／涂抹算法，不包含 macOS 的整笔画常驻 GPU 纹理、携色笔刷模型或液化累计位移场。重复液化重采样仍可能让像素变软；采样舍入边界可能有微小 CPU/GPU 差异，测试范围见上文。选区覆盖准备、回写像素仍由 CPU 完成，回读仍同步执行。普通画笔／橡皮／克隆／修复、透视变形与导出仍使用 CPU。

其他 GPU 操作仍有 a5 的重采样／描边抗锯齿差异与资源限制。8MP 限制针对上传的变形局部区域，而非整幅文档；更大请求回退 CPU。传输资源复用并非缓存所有计算临时纹理，也没有消除上传／回读或保证普遍提速。项目格式、运行时依赖与界面语言均不变。测试预发布版时请保留备份。
